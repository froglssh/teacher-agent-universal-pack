# Universal Presentation Deck Workflow

將任意主題、教材、文件、筆記或 repo 內容，轉成一份有清楚脈絡、可編輯、可驗證的 `.pptx` 簡報。預設不使用 AI 生圖或任何 API 金鑰；視覺以 PowerPoint 原生元件、PptxGenJS、表格、色塊、圖示、流程圖與簡潔版面完成。

## 先判斷工作模式

收到請求後，先判斷是否已足夠開始；只在必要時問一個最關鍵問題。

| 使用者狀況 | 工作模式 | 流程 |
| --- | --- | --- |
| 有主題或素材 | 全流程產製 | 引擎 1 -> 2 -> 3 -> 4 -> 5 -> 6 |
| 給一個 repo | repo-to-deck | 先盤點 repo，再跑全流程 |
| 有既有 `.pptx` | 診斷修改 | 引擎 4 + 5，必要時補引擎 3 |
| 只想定義模板 | 風格定義 | 引擎 5 |

若使用者直接給明確素材並要求產出簡報，可以直接開始。若缺少受眾、用途、時間或頁數，先補問最影響結果的一題。

## Repo-to-Deck 規則

當使用者給另一個 repo、資料夾或 GitHub URL：

1. 先讀 `README`、`AGENTS.md`、主要設定檔、docs、examples、入口檔與近期提交。
2. 判斷簡報目的：教學、介紹、操作說明、技術報告、產品提案、研究摘要或交接文件。
3. 不把 repo 檔案清單直接變成投影片；先萃取「人需要理解的主線」。
4. 每頁保留可追溯來源：在講稿備註或工作筆記中記錄對應檔案與段落。
5. 避免曝光密鑰、個資、內部 token、`.env`、私人設定。

## 引擎一：概念定位

目標：回答「這份簡報要讓觀眾帶走什麼」。

輸出：

```markdown
## 概念定位稿
### 總概念
[一句話]
### 三個子概念
1. ...
2. ...
3. ...
### 觀眾常見誤解或盲點
1. [盲點] -> [正確理解]
### 帶走一句話
[最重要的一句話]
### 最小事實包
- [必要資料、案例、定義、步驟]
### 投影片 vs 講稿分配
| 內容 | 建議位置 | 原因 |
```

## 引擎二：脈絡定位

目標：安排理解節奏，而不是只排章節。

通用三段：

| 段落 | 功能 | 佔比 |
| --- | --- | --- |
| 引起動機 | 讓觀眾知道為什麼要聽 | 15-20% |
| 建立理解 | 展開概念、證據、流程或案例 | 60-70% |
| 促成行動 | 收斂重點、決策、練習或下一步 | 15-20% |

每段輸出教學或溝通目的、放入內容、觀眾任務、建議頁數、入口、出口與常見設計錯誤。

## 引擎三：頁面架構

目標：每頁只有一個任務。

可用頁面角色：

| 角色 | 用途 |
| --- | --- |
| 封面頁 | 標題、副標、講者或專案 |
| 問題引入頁 | 用問題、痛點或情境建立動機 |
| 核心概念頁 | 定義主概念與一句話主張 |
| 比較頁 | 兩到三個選項、版本或概念對照 |
| 流程頁 | 步驟、路徑、工作流、時間線 |
| 架構頁 | 系統、組織、概念層級或模組關係 |
| 案例頁 | 具體例子、情境、before/after |
| 數據頁 | 指標、結果、比例、趨勢 |
| 操作頁 | 工具步驟、指令、畫面流程 |
| 風險頁 | 風險、限制、踩坑、注意事項 |
| 總結頁 | 收攏重點與帶走一句話 |
| 行動頁 | 決策、任務、練習、下一步 |
| 過渡頁 | 章節銜接 |

每頁要指定：頁碼、標題、頁面角色、本頁唯一主重點、建議頁型、觀眾任務、前後頁銜接、是否關鍵頁、建議 visual。

## 通用 Visual 版型

| visual | 用途 | PptxGenJS 作法 |
| --- | --- | --- |
| `comparison_table` | 比較選項、版本、方法 | `addTable`，強調關鍵欄或列 |
| `process_steps` | 步驟、流程、課程節奏 | 橫向卡片 + 箭頭 |
| `timeline` | 里程碑、歷史、專案進度 | 線段 + 節點 + 日期 |
| `architecture_map` | 系統、概念、組織架構 | 方塊、群組、連線 |
| `evidence_card` | 資料、引用、觀察、結論 | 數字或短句大字級 + 說明 |
| `before_after` | 修改前後、問題與解法 | 雙欄對照 |
| `checklist` | 檢核表、交付項、規則 | 勾選列 + 狀態色 |
| `quote_focus` | 關鍵句、原文摘錄、主張 | 大字句 + 來源小字 |
| `icon_grid` | 3-6 個並列重點 | 圖示/emoji + 標題 + 一行說明 |
| `code_or_command` | 指令、設定片段、程式流程 | 等寬字型區塊 + 註解標籤 |

visual 欄位範例：

```yaml
visual:
  type: comparison_table
  columns: ["方案", "優點", "限制", "適合情境"]
  rows:
    - ["A", "快", "彈性低", "短期交付"]
    - ["B", "可擴充", "建置較久", "長期維護"]
  emphasis_col: 2
```

```yaml
visual:
  type: process_steps
  steps:
    - title: "盤點素材"
      note: "找出主線與限制"
    - title: "建立架構"
      note: "每頁一個任務"
    - title: "生成驗證"
      note: "輸出 .pptx 並逐頁檢查"
```

## 引擎四：認知編修

用六個認知詞檢查每頁：

| 認知詞 | 做什麼 |
| --- | --- |
| 降雜訊 | 移除不幫助理解的元素 |
| 區塊化 | 同類資訊成組 |
| 增資訊 | 補上理解橋梁、標籤、例子 |
| 結構化 | 讓主從、因果、對照可見 |
| 順脈絡 | 排出合理閱讀順序 |
| 步驟化 | 把複雜任務拆成可跟上的步驟 |

診斷既有 `.pptx` 時，先擷取文字與縮圖，逐頁輸出「問題、原因、修改建議、優先級」。

## 引擎五：風格建構

先定骨架，再定風格。風格要服務理解。

預設規則：

- 16:9 寬螢幕。
- 每頁至少有一個視覺結構：表格、卡片、流程、圖示、色塊、示意架構。
- 不做純文字堆疊頁。
- 標題位置一致；同類頁型結構一致。
- 字級使用 55/34/21/13 比例作為起點。
- 中文優先用 `GenSekiGothic2 TW H` / `GenSekiGothic2 TW M`；未安裝時可退回微軟正黑體。
- PowerPoint 文字保持可編輯；不要把整頁輸出成不可編輯圖片，除非使用者明確要求海報式頁面。

輸出：

```markdown
## 風格設定摘要
- 視覺氣質：
- 主色 / 輔色 / 強調色：
- 字型：
- 版面規則：
- 圖表與 visual 規則：
- 不做事項：
```

## 引擎六：簡報總導演

目標：整合前五顆引擎，生成 `.pptx`。

技術執行：

1. 依頁面角色表寫 PptxGenJS 腳本。
2. 使用 PowerPoint 原生文字、表格、形狀、線條與圖示。
3. 若要處理數學符號，PowerPoint 採雙層文字框方案，避免把整頁轉圖。
4. 產出 `.pptx` 後，渲染縮圖逐頁檢查：對齊、重疊、可讀性、文字是否溢出。
5. 回報產出位置與需要人工確認的頁面。

若環境已有 `pptx` 或 `presentations` skill，讀取其技術規範並遵守；本 skill 負責內容工作流與頁面決策。

## 完成前檢查

- [ ] 總概念清楚，且每頁只有一個主重點
- [ ] 觀眾、用途、時間、頁數與交付格式明確
- [ ] 每頁有頁面角色與 visual 規劃
- [ ] 同類頁型一致，不同段落有節奏變化
- [ ] 字級、邊距、對齊、色彩一致
- [ ] 沒有洩漏密鑰、個資或 repo 私密設定
- [ ] `.pptx` 已生成並完成縮圖檢查
- [ ] 已告知檔案位置

## 給 Agent 的核心提醒

1. 不要把資料清單直接塞進投影片；先抽出觀眾需要理解的主線。
2. 預設零金鑰、可編輯、PowerPoint 原生元件優先。
3. 對使用者確認關鍵決策，但不要每一步都卡住；小型簡報可一次完成草稿。
4. 產出前必做視覺檢查，尤其是文字溢出與重疊。
5. 涉及本機檔案時，用清楚路徑回報。
